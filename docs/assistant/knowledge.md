## [doc] batch-expiry-implementation.md — ## Stock rules

## Stock rules

Physical stock is SUM(IN − OUT) across physical conditions, excluding lost. Available stock is eligible saleable stock minus reservations, clamped at zero in batch reporting. Condition changes create paired ledger entries and preserve physical quantity. Block/unblock records audit events without changing quantity.

Costs follow the existing stock service's weighted historical receipt cost per scope, rounded to two decimals; quantity × that cost provides valuation. This is the existing application method, not a newly introduced FIFO or moving-average accounting engine.

FEFO sorts eligible batches by expiry (undated last), then receipt/lot sequence. Existing explicit sales batch selection is preserved. Returns retain originating batch; non-saleable returns enter their physical condition. Posting and batch operations use transactions and locks; operation retry tokens prevent duplicate quantity postings.

## [doc] opening-stock-serials.md — # Opening Stock serial integration

# Opening Stock serial integration

Opening Stock accepts multiple serial assignments per item. Drafts store intent in JSON; they do not create serial records, make serials saleable, or post ledger/history entries. Posting validates again inside the voucher transaction and creates one quantity-IN ledger entry per serial using the existing `serial_id` link. Serial history records the voucher, user, location and effective opening date.

Existing serials are reusable only when they match business/product/variant/batch/branch/warehouse, both statuses are `in_stock`, condition is saleable, and there is no previous ledger entry, purchase/sale reference, customer/sold timestamp, or movement history beyond creation/metadata edits. New numbers must be unique across the business, including deleted records. Normalization follows the serial module: uppercase, ignoring whitespace and hyphens.

## [doc] settlement-reversal.md — # Receipt and supplier payment reversal

# Receipt and supplier payment reversal

Root cause: reverseJournalVoucher created opposite journal entries and marked only the original journal reversed. Receipt/payment source status, ledger_allocations and sales/purchase settlement fields were untouched. Ledger queries excluded reversed originals but included approved reversals, causing a double economic effect in displayed running balances.

Fix: lock and reload the source journal before reversal; reject duplicate reversal and reversing reversal journals. Preserve reversed original entries in ledger/cash-book queries. For receipt/payment journals, add negative compensating allocation records against the existing reversal's party journal line. Keep original allocations intact. Each compensation is identified by reversal entry plus original allocation ID, making reconciliation idempotent. Lock source documents, subtract reversed allocations from paid fields, update balance/payment status, mark receipt/payment reversed and link reversal_of_id. All changes occur transactionally. No migration.

Receipt entries: original Dr Cash 160 / Cr Receivable 160; reversal Dr Receivable 160 / Cr Cash 160. Supplier payment reversals use Dr Cash / Cr Payable. Both originals and reversals remain in audit history.

Verified local case: journal REC-2026-00002 (65), source receipt RCPT-2026-00002 (5), reversal REV-2026-00001 (66), sales invoice INV-2026-00025 (27). Applied allocation-only reconciliation to this confirmed existing reversal after rollback tests. No new journal/cash posting was created. Persisted invoice now paid 200, balance 160, status partial; customer ledger runs 360,160,0,160. Source receipt now reversed. Other historical settlements were not repaired in bulk.
